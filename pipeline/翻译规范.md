# 视频翻译配音 · 中文翻译规范

翻译这一步的产出直接决定配音能不能"配得牢"。这份规范把**翻译、时长预算、配音节奏**
三件事绑成一套账本——翻译时对着下游的真实时长账本写，而不是写完再让下游去提速、截断。

> 配套工具：`pipeline/validate_segments.py`。翻译前先跑它拿预算表，翻译后再跑它做校验。

---

## 一、翻译前必做：拿预算表

```bash
cd ~/Desktop/视频翻译项目
python3 pipeline/validate_segments.py runs/<ID>/03_transcript/segments.en.json --budget
```

它会输出每段的：**可用窗（秒）**、**预算字数**、**原文词数**、**段前可借静音（秒）**。

这张表的「预算字数」不是拍脑袋，是从 **7 部片子 527 段真实合成时长**回归出来的
中文朗读模型反推的：

```
朗读秒数 ≈ 0.1801 × 汉字数 + 0.0537 × 标点数 + 1.1234
```

解读这个模型（很重要，决定了怎么写译文）：

- **纯字速 5.55 字/秒**（1 ÷ 0.1801），比直觉快——中文本身念得很快；
- **每段固定开销 1.12 秒**：段首起音 + 句尾收尾 + IndexTTS 按标点切块时的块间静音；
- **每个标点额外 0.054 秒**：句内停顿；

**关键结论：短句的时间几乎全花在固定开销上，跟字数关系不大。**
所以"把译文写短"对 2-3 字的短句毫无用处——`小心！` 已是极限，再短就丢信息了。

---

## 二、翻译的四条硬优先级

写译文时，冲突一律按这个顺序取舍，**不许跳级**：

1. **信息完整** — 原文的每个信息点都要有中文对应。这是第一位的，任何情况下不许为了塞时间窗删句。
2. **口语自然** — 像中文配音演员会说的话，不是翻译腔。短句、主动语态、少用书面词。
3. **不超预算** — 对着预算字数写；写不下换更短的同义说法，但**不砍信息**。
4. **节奏贴合** — 句长与原片说话节奏大致同步（原片急的地方译文也要短促）。

> ⚠️ **关于信息完整性的重要说明**：
> 早期实践中，曾出现三句英文 "Let's play with some fun toys today. This depot looks cool. And it's time to play."
> 被过度压缩翻译为半句「来玩玩具啦，总站真酷！」——首尾两句整句丢失。
> 成因是将"语速上限"误当成了"强制删减指示"。
> **正确理解：预算是上限保护，不是删内容的许可。** 即使偶有超窗也应照实翻译，让下游动态借静音或微提速，
> 宁可语速稍快也绝不能丢失关键信息。

---

## 三、怎么用「预算字数」和「可借静音」

- **预算字数富余** → 正常翻译即可，别刻意拉长。
- **接近预算** → 优先用短词（"立刻"而非"马上立刻"，"走"而非"我们出发吧"）。
- **超预算但「可借静音」> 0.5s** → **可以照实写**。系统会把这句话往后铺进静音里，
  听感反而更自然，比硬压缩成短句强。
- **超预算且可借静音 ≈ 0** → 说明原片这段说话很紧凑。换更短的同义说法，
  仍然写不下就照实写，交给下游提速（≤1.25x 人耳几乎无感）。

### 好译文 vs 坏译文（真实例）

| 场景 | 原文 | ❌ 坏译文 | ✅ 好译文 | 说明 |
|---|---|---|---|---|
| 短促对话（窗 1.3s） | Look out, Mojo! | 小心啊摩乔你快看 | 小心！ | 窗太窄，短促才对得上原片节奏 |
| 短促对话（窗 1.3s） | She's definitely done that before! | 奶奶以前肯定练过这个 | 奶奶练过！ | 中文固定开销大，长句必然被提速到失真 |
| 三句合并段（窗 5.7s） | Let's play with some fun Tayo toys today. This bus depot looks cool. And it's time to play. | 来玩TAYO玩具啦，总站真酷！ | 今天来玩好玩的TAYO玩具吧。这个车厂真酷。该玩啦！ | **三句都要有**，宁可超窗也不许删句 |
| 专有名词 | Manny / Mojo / Titipo | 曼尼 / 摩乔 / 提提波 | 同左（全片统一） | 人名音译必须统一 |

## 四、语言与术语约定

- **口语化短句**：每句尽量不超过 20 字，长句按语义断成两句（用句号/感叹号，不要用逗号堆叠）。
- **人名音译统一**：Titipo=提提波、Manny=曼尼、Mojo=摩乔、Bo=小波、Tayo=泰友。
  全片首次出现后保持同一写法。
- **英文词与数字**：会走 `index-tts/checkpoints/glossary.yaml` 的发音表。
  新出现的英文词/型号（如 GPT-5）先加进 glossary，别让模型自己猜：
  ```yaml
  TAYO: {zh: "泰友"}
  ```
- **用上下文修 ASR 错听**：ASR 在音乐段会听错（"Fact 4/5" 被听成 "FAT"），
  按上下文改成合理内容，不要照抄错字。
- **标点必须保留**：TTS 靠标点断句。字幕层的去标点由 `build_subs.py` 自动处理，
  **不要**在 `segments.zh.json` 里去标点。

## 五、翻译后必做：校验

```bash
python3 pipeline/validate_segments.py runs/<ID>/03_transcript/segments.en.json \
  runs/<ID>/04_translate/segments.zh.json
```

输出分三类，处理方式不同：

| 输出 | 含义 | 怎么处理 |
|---|---|---|
| `ERROR:` | 破坏段落契约（改时间戳/改 id/段数不符/空译文） | **必须修**，exit 1 不进 TTS |
| `WARN: 疑似漏译/压缩过度` | 英文词数 ÷ 中文字数 ≥ 1.8 | **必须补全内容**（不是缩短！） |
| `WARN: 建议缩短译文` | 内容确实写太长，可精简 | 精简措辞，只砍语气词不砍信息词 |
| `物理极限段` | 窗 <1.9s，译文已到极限字数 | **不用改**，下游会自动借静音/微提速 |
| `需提速段` | 略超窗，1.2x 内可救 | 通常不用改，下游提速吸收 |

**看到"物理极限段"不要慌，也不要为它删内容**——那是中文固定开销撞上原片紧凑短句的
物理结果，已在设计内由下游吸收。

## 六、质量红线（交付前自查）

1. 每条英文的**信息点都有中文对应**，没有整句消失；
2. 人名、专有名词**全片统一**；
3. 短促对话段（预算 ≤3 字）译文**短促有力**，不是长句被提速；
4. 时间戳、id、段数与 `segments.en.json` **完全一致**（校验脚本硬保证）；
5. 校验脚本 exit 0 或仅剩"物理极限段"提示。
